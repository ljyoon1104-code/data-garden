# 구버전·수정본 혼용과 공용 PC 전체 삭제 검증

검증일: 2026-11-11. 가상 자료와 격리된 로컬 환경만 사용했다. 커밋·푸시·배포·원격 설정 변경은 하지 않았다.

## 버전과 격리 범위

- 공개 배포 기준: `4230593079849ed03d540ae602d6e72637efc15c`. 읽기 전용으로 확인한 최근 [Pages 실행 39378985696](https://github.com/ljyoon1104-code/data-garden/actions/runs/39378985696)은 main push에 대한 성공 실행이며 같은 SHA다.
- 구버전은 해당 Git 이력을 별도 임시 사본으로 추출해 빌드했다. 현재 작업 폴더를 checkout/reset하지 않았다. 구버전 lockfile과 일치하는 설치 패키지 94개의 버전을 확인해 재사용했다. 공개 서버의 기존 산출물과 바이트 단위로 같다고 주장하지는 않는다.
- 비교 대상은 삭제 세대 검사가 이미 있는 로컬 연결 버전 1 수정본과, 이번 연결 버전 2 최종 수정본이다. 공개 구버전은 삭제 세대 검사가 없으며 `indexedDB.open(name, 1)`을 호출한다.
- 최종 격리 빌드의 런타임·설정·public 파일 105개는 현재 작업 폴더와 SHA-256이 일치한다. 집계 소스 SHA-256은 `eb68af6df01b65015f39185676eea78f29ca39eeb0c4431cb915e2a9d6163dfd`이며, 산출 방법은 `SHA256(JSON.stringify(sourceHashes))`다. 기존 루트 `dist` 29개 파일은 변경하지 않았다.
- 프로젝트 스키마 6 및 JSON 백업 형식 1과 IndexedDB 연결 버전은 별개다. 연결 버전 2 이행은 프로젝트나 기존 삭제 기록을 지우지 않는다.

## 발견한 결함과 수정

삭제 기록만으로는 그 기록을 읽지 않는 구버전 클라이언트를 제약할 수 없다. 연결 버전 1을 유지한 대조 시험에서 전체 삭제 뒤 구버전 방식의 저장이 프로젝트를 다시 만들었다. 정상적인 두 탭은 기존 Web Lock으로 쓰기 탭이 하나이므로, 두 탭이 항상 동시에 저장한다고 해석해서는 안 된다. 저장 경계 시험과 일반 사용자 업데이트 흐름을 구분했다.

이번 수정은 기존 저장소 이름·배포 경로·쓰기 잠금을 유지한다.

1. IndexedDB 연결 버전을 2로 올린다. 공개 구버전의 `versionchange` 처리기가 연결을 닫는다. 시작된 트랜잭션이 끝나야 버전 이행이 완료되므로, 이전 쓰기가 먼저 완료되더라도 이후 명시적 전체 삭제에 포함된다.
2. 닫힌 구버전 연결의 뒤늦은 저장은 `InvalidStateError`, 구버전의 버전 1 재열기는 `VersionError`로 거절된다. 수정본끼리는 기존 삭제 세대 검사를 계속 적용한다.
3. 멈춘 탭이 버전 이행을 막으면 오류를 표시한다. 실패한 열기 요청은 뒤늦게 연결이 해제되어도 이행 트랜잭션을 중단한다. 삭제를 수행하거나 성공으로 표시하지 않는다.
   실제 Chromium에서는 완전히 멈춘 탭의 `versionchange` 전달을 기다리는 동안 `blocked`도 오지 않아 45초 넘게 시작 화면에 머물렀다. 이를 보강해 연결을 10초 안에 완료하지 못하면 오류를 표시하고 초기 쓰기 잠금을 해제한다. 탭이 다시 실행될 때 남아 있던 열기 요청도 같은 실패 처리로 중단한다.
4. 초기 저장소 연결에 실패하면 수정본이 획득했던 쓰기 잠금을 해제한다. 오류 안내에는 다른 탭을 닫고 사용자가 새로고침할 수 있는 경로를 제공한다.
5. 전체 삭제 안내는 수정본 탭의 화면 비우기와, 구버전에 남는 메모리·백업을 구분한다.

10초는 실행 중인 탭의 연결 대기 타이머다. 브라우저가 해당 탭 자체를 멈춘 동안의 실제 시간까지 보장하지 않는다. 오류 처리 직전 이미 끝난 비파괴 버전 이행을 되돌리는 기능도 아니다. 이 경우에도 연결 이행 자체로 프로젝트를 삭제하지 않으며, 실패 이후 연결을 사용하지 않는다.

## 보장 범위와 남는 자료

- 최종 수정본이 연결 버전 2 이행을 마치고 전체 삭제에 성공하면, 이번에 확인한 공개 구버전의 버전 1 저장 경로로 삭제된 프로젝트를 다시 저장할 수 없다. 삭제 후 새로 만든 프로젝트는 현재 삭제 세대로 정상 저장할 수 있다.
- 이미 실행 중인 구버전의 화면과 메모리, JSON 백업 코드는 소급해서 회수할 수 없다. 구버전 읽기 전용 탭도 이전 자료를 계속 표시하고 백업할 수 있다. 새 Service Worker의 제어를 받는다는 사실만으로 구버전 JavaScript가 교체되지는 않는다.
- DB 연결 종료는 구버전의 Web Lock을 해제하지 않는다. 구버전 쓰기 탭이 남아 있으면 수정본은 읽기 전용일 수 있다. 잠금을 강제로 빼앗거나 잠금 이름을 바꾸지 않았다.
- 전체 삭제는 해당 배포 경로의 프로젝트 본문과 화면 설정·목록·최근 선택을 비우고, 자료가 없는 초기화 표시와 삭제 세대만 남긴다. 프로그램 캐시, 다른 앱·배포 경로의 저장소와 내려받은 백업·출력 파일은 유지한다. 보존한 백업을 사용자가 명시적으로 복원하면 새 사본을 만들 수 있다.
- 이 변경은 확인한 구버전과 수정본의 저장 일관성 대책이다. 같은 출처의 임의 코드에 대한 접근 제어 수단은 아니며, 전용 호스트 분리 여부는 [호스트 이전 검증](hosting-migration-verification.md)의 별도 결정 사항이다.

## 자동 회귀 검사

[추가 회귀 테스트](../src/persistence/mixed-version.test.ts)는 6개 사례를 포함한다. 삭제 세대를 모르는 버전 1의 재저장 재현, 기존 삭제 기록 유무에 따른 비파괴 이행 2개, 진행 중 저장 완료→버전 이행→전체 삭제→뒤늦은 저장·재연결 차단과 새 프로젝트 저장, 막힌 이행 실패→지연된 자동 이행 중단→재시도, 차단 알림조차 전달되지 않을 때의 정확한 10초 한도·자료 보존·지연 이행 중단·재시도를 확인했다.

## 실제 브라우저 검증

검증 전용 Edge 157 프로필과 임의의 loopback 포트를 사용했다. 브라우저를 직접 실행하고 기본 초점 모의를 끈 CDP 연결로 조작했다. 구버전 쓰기 탭의 실제 `hidden` 상태와 읽기 탭의 `visible` 상태를 확인했다. 각 시험 안에서는 주소·`/data-garden/` 경로·`data-garden:%2Fdata-garden%2F` 저장소가 동일하다. 기존 사용자 프로필이나 공개 앱에는 시험 자료를 넣지 않았다.

시험용 서버에서 정적 빌드를 바꾸되 기존 해시 자산도 제공했다. 탭의 실제 main URL과 제공 파일 SHA-256을 대조했다. SW URL은 같으므로 시험용 응답 계측으로 실제 캐시 ID·파일 목록도 확인했다. 계측 응답 외 SW 저장·갱신 동작과 배포용 소스는 바꾸지 않았다. 새 SW가 제어하는 구버전 main 탭과 새 main 탭이 동시에 열린 것을 확인했다.

수정 전 대조 시험은 `http://127.0.0.1:57644/data-garden/`에서 6개 단계가 완료됐다. 구버전 main은 `index-DU_b2GCw.js`, 이행 장벽이 없는 로컬 수정본은 `index-J0xKmmG7.js`였다. SW 캐시 버전은 각각 `12421b218c99b053`과 `085edc9878aa0ee9`다.

| 저장 권한 재확인 | 수정본 쓰기 탭을 닫아도 구버전 읽기 탭은 초점 복귀만으로 쓰기 권한을 얻지 않았다. 그 탭을 새로고침하면 최종 main과 연결 버전 2로 열려 쓰기 권한을 얻었고, 빈 자료와 새 프로젝트 저장을 확인했다. |
| 새로고침·브라우저 재접속 | 삭제 후 만든 새 프로젝트만 저장했다. 새로고침과 브라우저 정상 종료 뒤 같은 독립 프로필·같은 주소로 재접속했을 때도 새 프로젝트만 남았다. 삭제 전 프로젝트는 돌아오지 않았다. |
| 삭제 알림을 처리하지 않는 구버전 | 구버전은 삭제 알림 처리 코드 자체가 없다. 이 탭의 저장 차단은 알림 수신이나 활성화 상태가 아니라 버전 2 이행과 연결 종료에 의해 적용됐다. |
| 완전히 멈춘 구버전 탭 | `Page.setWebLifecycleState(frozen)`으로 구버전 읽기 탭을 멈췄다. 수정본에서 연결 대기 오류를 표시했고 writer 잠금은 0개였다. 삭제 확인 문구를 입력해도 확정 버튼은 비활성이며 성공 문구는 없었다. 구버전 탭을 다시 실행시킨 뒤 지연된 이행은 중단됐고 연결 버전 1·기존 프로젝트가 보존됐다. 수정본 새로고침 후 버전 2 이행과 실제 전체 삭제가 성공했다. |

최종 같은 빌드로 아래 4개 흐름, 총 30/30단계를 통과했다. 각 시험은 별도 독립 프로필이며, Edge 버전은 `157.0.4341.42`다. 주소는 시험 당시 주소이며 검증 서버와 브라우저는 종료했다.

| 흐름 | loopback 포트 | 단계 | 로컬 증거 폴더 |
| --- | --- | --- | --- |
| 일반 UI 업데이트 | 56150 | 7/7 | `browser-j805sY` |
| 예약·뒤늦은 저장 주입 | 50274 | 8/8 | `browser-cuBIai` |
| 진행 중 저장 주입 | 55883 | 8/8 | `browser-CjgDuq` |
| 멈춘 구버전 탭 | 56522 | 7/7 | `browser-xhHpdm` |

진행 중 저장의 실제 epoch 밀리초 순서: 구버전 쓰기 트랜잭션 시작 `1794363651245` → 수정본 `open(v2)` 요청 `1794363653004` → 구버전 쓰기 완료 `1794363653090` → `upgradeneeded 1→2` `1794363653186` → 버전 2 연결 완료 `1794363653214`. 열기 요청 시점에 구버전 화면은 ‘저장 중’이었고 수정본 연결은 아직 없었다. 단위 테스트의 순서 보장뿐 아니라 실제 브라우저 트랜잭션과 화면을 함께 확인했다.

완전히 멈춘 탭 시험은 `http://127.0.0.1:56522/data-garden/`의 독립 프로필에서 7/7단계를 통과했다. 한도 보강 전 빌드 `index-CruyMTI8.js`에서 45초 넘게 시작 화면에 머물던 증거와, 멈춘 탭을 다시 실행시키면 이행이 진행되던 증거도 별도로 보존했다. 이는 새 대기 한도가 필요한 이유이며 삭제 성공으로 판단한 사례는 아니다.

로컬 증거는 Git에서 제외되는 `tmp/mixed-version-reset-Entmeb`에 보관했다. `evidence-summary.json`과 각 흐름의 `results.json`에 main·SW 해시, 실제 저장소·탭 상태, 다운로드 해시, 트랜잭션 시각을 기록했다. 현재 탭의 삭제 후 빈 표·선택 없음과 구버전 탭의 12행·6열 잔존 화면도 캡처해 확인했다. 페이지 예외는 없었지만 구버전의 예상된 저장 차단 오류와 PWA 준비 실패 안내는 화면 기록에 남아 있으므로 ‘화면 오류 0개’라고 해석하지 않는다.

검증 범위는 이 Edge 버전의 로컬 신뢰 출처와 확인한 공개 구버전이다. 다른 브라우저·다른 과거 앱 버전·실제 공개 HTTPS 배포의 갱신은 이번에 시험하지 않았다. 이미 내려받은 파일과 다른 앱 저장소의 보존은 기존 [공용 PC 삭제 시험](public-pc-reset-verification.md)의 범위도 함께 참고한다.

## 배포 전과 공용 PC 사용 후 절차

1. 필요한 JSON 백업을 먼저 내려받아 별도 보관한다.
2. 기존 쓰기 탭에서 앱이 제공하는 저장 후 업데이트를 적용하거나, 필요한 백업 뒤 모든 구버전 탭을 닫고 최신 앱에 다시 접속한다. 구버전 읽기 전용 탭의 업데이트 버튼은 비활성이므로 해당 탭은 닫고 다시 연다.
3. 수정본이 읽기 전용이면 구버전 쓰기 탭을 닫고 수정본을 새로고침한다. 저장소 업데이트 차단 오류가 나면 다른 탭을 닫고 재시도한다. 오류 상태를 삭제 완료로 간주하지 않는다.
4. 수정본에서 실제 전체 삭제를 실행하고 빈 프로젝트 목록을 확인한다. 공용 PC를 떠나기 전에는 자료가 메모리에 남을 수 있는 모든 구버전 탭을 닫는다. 다운로드 폴더의 파일은 별도로 정리한다.
5. 향후 승인된 배포 후 실제 HTTPS·Service Worker 업데이트 경로에서 같은 절차를 재확인한다. 이번 로컬 검증만으로 공개 배포가 갱신되지는 않는다.
