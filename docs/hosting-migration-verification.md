## 전용 출처 설계와 사용자 결정

새 HTTPS 호스트 아래에는 데이터뜰과 검토된 부속 자산만 배포한다. 다른 앱·사용자가 올린 실행 가능한 HTML을 같은 호스트의 다른 경로에 함께 두지 않는다. 같은 `github.io` 호스트의 새 저장소나 경로는 격리 방안으로 인정하지 않는다. [동일 출처 정책](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Same-origin_policy), [IndexedDB 출처 경계](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API/Basic_Terminology).

아직 필요한 결정은 호스팅 사업자·관리 계정, 사용할 전용 호스트, 보유 도메인 사용 여부와 갱신 책임, 응답 보안 헤더 제어의 필요 수준이다. 주소를 임의로 예약하거나 설정 파일에 가상의 도메인을 넣지 않았다.

| 후보 | 비용·관리 | 조건과 제약 |
| --- | --- | --- |

현재 공개 응답에서 HSTS는 관찰됐고 CSP·X-Frame-Options·X-Content-Type-Options·Referrer-Policy·Permissions-Policy 응답 헤더는 없었다. 도메인 변경 자체는 이 헤더를 추가하지 않는다. 정적 응답의 `Access-Control-Allow-Origin: *`도 다른 출처의 IndexedDB 접근 권한을 주지는 않는다. 이번 작업은 헤더나 배포 권한을 변경하지 않았다.

검증 도구의 실패도 보존했다. 최초의 그래프 선택자 오류, 날짜 열에 문자열을 넣은 잘못된 시험 입력은 도구 조건을 고쳐 다시 확인했다. 본 검증 7단계는 통과했지만 마지막 오프라인 단계에는 의도적으로 새 자료를 입력한 프로젝트까지 ‘불변’으로 비교한 잘못된 가정이 있었다. 이 실패 기록을 지우거나 전체 본문 통과로 바꾸지 않았다. 같은 B 주소·프로필에서 새 입력 프로젝트를 분리한 **후속 오프라인 4/4 검사**와 오류 안내·A 전용 표식 **2/2 검사**가 종료 코드 0으로 통과했다. 표식 검사에서도 A의 프로젝트는 최초 A 백업과 정확히 같았고 A 2개·B 10개 프로젝트는 변경되지 않았다. 서버 중복 종료를 기다리던 검증 도구의 정리 코드를 고친 뒤 정상 종료도 확인했다. 앱 소스 결함으로 판정한 사항은 없다.

## 실제 이전 순서와 배포 후 확인

1. **기존 주소에서 백업:** 각 기기에 저장된 필요한 프로젝트를 기존 앱의 JSON 백업 버튼으로 내보낸다. 파일을 열 수 있는지·크기·해시와 보관 위치를 확인한다. 기존 주소·QR·앱·백업 버튼을 유지하고 자동 리디렉션이나 저장소 삭제를 하지 않는다.
2. **새 주소 배포:** 승인된 최종 수정본을 별도 전용 호스트에 병행 배포한다. 기존 Pages에 도메인을 바로 연결해 구 주소를 먼저 리디렉션시키는 방안은 초기 이전 수단으로 사용하지 않는다. 동일 Pages 서비스가 필요하다면 구 앱 접근을 보장할 별도 사이트/배포 구성을 먼저 결정한다.
3. **복원·저장 확인:** 새 출처에 JSON을 사본 복원하고 자료·과거 버전·세 분석·그래프·해석·이력과 저장 상태를 확인한다. 새로고침·재접속·오프라인도 확인한다. 한도 초과면 구 앱의 프로젝트와 원본 백업을 보존한 채 필요한 프로젝트/결과를 나눈 검증 사본을 준비한다. 자료를 몰래 잘라 복원하지 않는다.
4. **새 QR 배포:** 새 주소의 HTTPS·기능·저장·백업 재열기를 확인한 뒤 새 QR과 안내를 배포한다. 구 QR의 사용자는 기존 주소에서 백업할 수 있어야 한다.
5. **기존 주소 안내 정비:** 충분한 이전 기간과 사용자 확인 후 기존 주소의 안내를 정비한다. 먼저 일괄 리디렉션하지 않는다. 부득이하게 리디렉션한다면 미이전 사용자의 구 출처 백업 경로를 실제 검증한 뒤 적용하며, 구 프로젝트·캐시는 자동 삭제하지 않는다.

실제 배포 후에는 선택한 HTTPS 호스트·인증서·도메인 소유권/갱신·다른 앱 미배포·보안 헤더·SW 범위·manifest 설치 정체성·OS PWA 설치/업데이트·기존 QR 접근을 다시 확인해야 한다. 이번의 loopback 출처 격리와 오프라인 성공을 실제 공개 호스트 분리 완료로 해석하면 안 된다. 호스팅 서버가 정상 정적 접속 로그를 남기는 것과 앱이 프로젝트를 업로드하지 않는다는 것도 구분한다.

## 변경과 검사 범위

- 이번에 Git 변경으로 추가한 파일은 이 문서 하나다. 나머지 자료·검사 도구·프로필·화면은 Git 무시 대상 전용 tmp에 있다. 기존 미커밋 보안 수정 35개 파일은 그대로 보존했다.
- 시작 시 기록한 기존 관리 대상 172개 파일의 바이트 SHA-256이 모두 같고, 기존 검증 자료 26개와 생성 스크립트도 변경하지 않았다. `node scripts/create-fixtures.mjs --check`는 26개 일치·0개 실패였다.
- 이전 자료 생성/호환성 24개, 비교 도구의 변경 탐지·보존 24개 단언이 통과했다. 가상 자료 기본 manifest 5항목·추가 manifest 13항목의 크기/해시와 실제 UI 백업의 의미 비교를 확인했다. 문서 상대 링크와 `git diff --check`도 검사했다.
- 앱 소스·설정·의존성 변경이 없어 이번 작업에서 전체 타입 검사·npm test·빌드·캐시 빌드를 다시 실행하지 않았다. 이전 보안 작업의 334개 테스트 통과를 이번 작업의 새 실행 결과로 보고하지 않는다. 대신 기존 최종 빌드를 실제 두 출처·서버 중지·브라우저 재시작에서 검증했다.
- 커밋·푸시·배포·호스트/DNS/Pages/계정 설정 변경은 수행하지 않았다. 최종 Git HEAD와 origin은 시작 시와 같다.
