## 한도와 검사 시점

바이트 한도의 `KiB`·`MiB`는 각각 1,024·1,048,576바이트다. 문자열 한도의 UTF-16 코드 단위는 JavaScript 문자열 길이 기준이며, 이모지 등의 서로게이트 쌍은 2단위다. 작업량 단위는 시간이나 바이트가 아닌 코드상의 보수적 반복 비용 추정치다.

| --- | --- |
| CSV 파일·필드·레코드 | 파일 읽기 전 20 MiB. 64 KiB `File.slice` 조각을 읽어 디코딩한다. 필드 65,536 UTF-16 단위, 논리 레코드 1,048,576단위를 읽는 중 검사한다. 레코드 한도에는 인용·구분자와 셀 내부 줄바꿈이 포함되고 레코드 끝 줄바꿈은 제외된다. |

한도 초과를 값 잘라내기·0/결측값 대체로 성공 처리하지 않는다. 오류 안내 후 자료·시트·프로젝트를 나눠 다시 시도해야 한다. 암호·분할 ZIP·ZIP64·일부 비표준 ZIP은 일반 XLSX 사본으로 다시 저장해야 한다.

## 낮은 자원으로 확인한 경계 사례

- 깊이 2·토큰 4·문자열 3단위의 작은 시험 한도로 이스케이프된 서로게이트 쌍·따옴표, 키와 컨테이너의 토큰 계산을 검사했다. 실제 최대 메모리를 소진할 필요 없이 선행 차단을 확인한다.
- 3개 CSV 조각 중 두 번째에서 50,000행을 초과하게 만들었다. `File.arrayBuffer`는 호출되지 않고 첫 두 조각만 읽으며, 세 번째의 잘못된 UTF-8을 읽기 전에 행 한도 오류가 발생했다. 열·빈 셀 보정 한도도 뒤의 미닫힌 따옴표보다 먼저 차단된다.
- 4,000행·100구간 히스토그램 30개는 복원하고, 48개는 모두 재계산하기 전에 공용 예산에서 거절한다. 그래프 수 자체를 임의의 새 고정 한도로 바꾼 것이 아니다.
- 600행·k=200인 저장 이웃 회귀 하나는 복원하지만 4개 반복은 모든 평가를 마치기 전에 거절한다. 군집 1,000행의 정확 실루엣 반복과 연관 검증도 같은 예산을 소모한다.
- 정상 크기의 가공 설정이라도 큰 설명 문자열을 가진 계보를 여러 분석이 반복 검증할 때는 그 크기를 차감한다. 테스트는 실제 과다 계산에 들어가기 전 차단되는지를 호출 감시로 확인한다.
- CSV의 두 번째 BOM까지 제거하던 처리를 고쳤다. 첫 BOM만 파일 표식으로 제거하며, 실제 두 번째 BOM은 값으로 남는다. 닫는 따옴표 뒤 허용 공백의 EOF 처리와 CP949 문자 경계도 검사했다.

이 검사는 제한 장치가 작동하는지 보여준다. 학교 PC의 최소 RAM이나 모든 한도 내 프로젝트의 최대 메모리·응답 시간을 측정한 성능 보증은 아니다.

## 자동 검사와 재현

최종 소스에서 타입 검사, 전체 **334개 테스트**, 빌드, 산출물·오프라인 캐시 검사(**28개 파일**)가 통과했다. 기존 검증 자료 **26개**는 생성 결과와 일치했고 기존 파일을 검사에 맞춰 변경하지 않았다.

~~~sh
npm run typecheck
npm test
npm run build
npm run check:build
node scripts/create-fixtures.mjs --check
node scripts/security-fixtures.mjs --check tmp/security-audit-20261110T054624308Z-b75eed9a
~~~

새 가상 보안 자료를 만들 때는 소스를 고정한 뒤 `node scripts/security-fixtures.mjs --generate`를 실행한다. 매번 새 Git 무시 폴더를 만들며 기존 자료를 덮어쓰지 않는다. `--check`는 생성 파일의 바이트·해시와 현재 소스 해시를 확인한다. manifest의 18개 기대 결과는 생성할 때 실제 앱 함수로 확인한 것이며, `--check` 자체가 모든 브라우저 동작을 다시 실행하는 명령은 아니다.

주요 추가 회귀 검사는 `csv-input.test.ts`, `xlsx-import.test.ts`, `import-diagnostics.test.ts`, `backup-limits.test.ts`, `wrangling-work.test.ts`, `analysis-budget.test.ts`, `output.test.ts`에 있다. Windows 제한 환경에서 Vitest 임시 경로 오류가 생기면 README의 TEMP/TMP 안내를 따른다.

## 실제 로컬 브라우저 재검증

별도 Edge `157.0.4341.42`의 새 브라우저 컨텍스트와 `http://127.0.0.1:63205/` 서버에서 위 소스 해시의 앱을 검증했다. 기존 사용자 탭·프로젝트는 건드리지 않았다. `browser-results.json`과 `browser-output-check.json`에 **18/18단계 통과**, 콘솔 오류·실패 요청·외부 요청 각 **0개**를 기록했다. 공개 Pages의 재검증 결과와 구분한다.

- 정상·조각 경계·EUC-KR CSV, 필드/행 한도 오류, 정상 XLSX·손상된 미선택 시트·손상된 선택 시트·범위 초과를 실제 파일 입력으로 확인했다.
- 정상·schema 1·깊은 JSON·손상 UTF-8·반복 그래프 30/48개 백업을 실제 복원 화면에서 확인했다. 실패·취소 후 IndexedDB의 모든 기존 프로젝트 지문과 새로고침 후 내용을 비교해 보존을 확인했다.
- 실행 중 CSV·JSON 작업 취소, 입력 화면 닫기, 파일·인코딩·구분자·시트 변경을 확인했다. 실제 Worker 진행 뒤 취소 요청과 `terminate`가 관찰됐으며, 생성된 Worker 85개 모두 종료됐다. 별도로 이전 실제 완료 메시지를 합성 재전달해 JobGate의 이전 응답 차단도 확인했다. 이는 종료한 Worker가 스스로 늦게 응답한 관측과는 구분한다.
- 안전 CSV와 명시적 셀 자료형 XLSX를 실제 내려받았다. 정상 CSV 3행은 일치했고 XLSX 첫 시트 자료 26행과 머리글의 문자열 셀 54개 및 모든 시트의 수식 셀 0개를 검사했다.
- 오프라인에서 CSV·XLSX 입력과 JSON 복원을 확인했다. 28개 앱 캐시 항목에 사용자 파일 이름 경로가 포함되지 않았다. 관찰한 가상 자료 흐름에서 외부 요청은 없었다.
- 실제 출력·완료 화면 캡처를 확인했고 이 검증용 서버와 브라우저만 종료했다.

## 실제 Excel 열기·저장·재열기

Windows의 실제 Excel `16.0.10417.20228` x64, 한국어 `ko-KR`, 목록 구분자 쉼표에서 UI를 조작했다. 연결된 Excel 문서 도구는 세션이 없었으므로 Windows 앱 조작 도구를 사용했다. 임의 COM 자동화나 보안 설정 변경은 하지 않았다. 기존 검증 창의 오래된 마법사만 취소하고, 가상 검증 문서만 열고 닫았다. Excel 앱과 다른 사용자 창은 종료하지 않았다.

최종 코드로 생성한 CSV 27개 허용 사례에는 정상 한글·쉼표·따옴표·LF/CR/CRLF, 실제 숫자 -5/0/5, 숫자 모양 문자열, ASCII·전각 수식 시작 문자와 BOM·제로폭 접두사를 포함했다. 세미콜론·탭·파이프·줄바꿈 뒤 수식 및 비가시 접두사의 26개 조합은 앱 안전 모드에서 거절되므로 위험 CSV를 Excel에 억지로 입력하지 않았다. 전체 53개 사례는 명시적 셀 자료형 XLSX로 확인했다. 줄바꿈 없는 24개 CSV는 원문을 수정한 파일이 아니라, 별도 사례 부분집합을 같은 앱 직렬화 함수로 새로 생성한 대조 자료다.

| 경로·설정 | 첫 열기 | Excel 저장·닫기·재열기 | 실제 셀 검사 결과 |
| --- | --- | --- | --- |
| 일반 열기 `Ctrl+F12` → 구형 텍스트 마법사, UTF-8·쉼표만·따옴표 한정자·일반 | 이 설치에서는 일반 열기가 구형 마법사로 연결됐다. 줄바꿈 없는 24개 사례를 2열로 불러왔다. | 첫 셀 상태를 `excel-legacy-first.xlsx`로 기록하고, CSV UTF-8로 저장한 뒤 닫고 같은 일반 열기·마법사로 재열어 `excel-legacy-reopened.xlsx`로 기록했다. | 두 사본의 24개 사례 값·형식 동일, 모든 시트 수식 0개. 실제 -5/0/5는 숫자, 보호된 수식 문자열은 작은따옴표가 남은 문자열이었다. 원래 문자 0/5는 일반 형식에서 숫자로 추론됐다. |
| 데이터 → 텍스트/CSV(Power Query), UTF-8·쉼표·첫 200행 형식 검색 | 정상 줄바꿈을 포함한 27개 사례를 모두 읽었다. 기본 Column1/Column2 머리글이 추가되고 CSV 머리글도 데이터로 유지되는 설정이었다. | `excel-modern-first.xlsx`로 첫 셀 상태를 기록한 뒤 CSV UTF-8로 저장·닫기, 새 검증 통합 문서의 같은 가져오기 방식으로 재열어 `excel-modern-reopened.xlsx`로 기록했다. | 사례 ID로 비교한 27개 값·형식 동일, 수식 0개, 보호 접두사 유지. 이 혼합 열의 실제 숫자도 문자열로 가져와졌다. 일반 열기의 숫자 추론과 구분한다. |
| 구형 마법사에서 정상 줄바꿈 CSV | 인용된 단독 LF가 추가 행으로 표시됐고 완료 시 ‘파일을 완전하게 로드하지 못했습니다’ 경고 후 첫 3행만 남았다. | 이 부분 상태를 별도 CSV로 저장했으나 전체 자료의 재열기 성공 증거로 사용하지 않는다. | 실제 데이터 손실을 동반하는 가져오기 호환성 문제다. 뒤쪽의 수식 사례가 로드되지 않았으므로 이 실패를 수식 보호 성공이나 우회 증거로 삼지 않는다. 정상 여러 줄 자료는 현대식 가져오기 또는 XLSX를 사용한다. |
| 명시적 자료형 XLSX 일반 열기 | 53개 사례가 열렸다. 수식 모양 문자열과 실제 숫자를 별도 셀 형식으로 유지했다. | Excel에서 `excel-typed-saved.xlsx`로 저장·닫기·재열기 후 `excel-typed-reopened.xlsx`로 상태를 다시 기록했다. | 53개 원본 값·형식 동일, 모든 시트 수식 0개. 실제 숫자 -5/0/5는 숫자, 문자 -5/0/5는 문자열, LF·CR·CRLF·전각·비가시 문자도 보존됐다. |

화면 값만으로 수식 여부를 판단하지 않았다. 위 XLSX는 실제 Excel이 저장한 파일이며, 저장 후 파일의 `.t`·`.f`와 raw OOXML `<f>`·공유 문자열을 검사했다. CSV 저장 바이트의 실제 보호용 작은따옴표도 확인했다. `excel-inspection.json`(최종 검사 UTC `2026-11-10T06:07:55.840Z`)에 파일별 생성/수정 시각·SHA-256·셀 형식·수식·문자 코드와 경로별 비교를 기록했다. CSV는 빈 문자열/null, 숫자 모양 문자열, 불리언의 원래 형식을 완전히 보존하지 않는다.

마법사의 일부 전환에서 ‘응답 없음’과 조작 도구 시간 초과가 발생했다. 같은 동작을 계속 보내지 않고 대기·프로세스 경로로 창 재선택 후 상태를 확인해 이어갔다. 강제 종료는 하지 않았다. 별도의 마법사 없는 자동 열기 경로, 다른 Excel 버전·지역 설정과 LibreOffice는 미검증이다.

독립적으로 확인한 라이브러리 제한: 앱이 작성한 XLSX XML에는 CRLF의 CR이 `_x000d_`로 남지만, SheetJS 0.20.3의 `xlsx.mjs` 3928~3930행은 재읽을 때 CRLF를 LF로 정규화한다. 최종 브라우저 출력에서도 문자열 4개의 이 정규화를 확인했다. 이 라이브러리 재읽기 결과를 파일에서 CR이 삭제됐다는 근거로 삼으면 안 되며, 실제 Excel의 셀 값과 구분해 판단해야 한다.

## 유지된 보호책과 남은 제한

- 원본·과거 버전 보존, ID 기반 참조, 유효성 검사 후 별도 사본 복원, IndexedDB 저장의 원자성과 쓰기 탭 제어를 유지했다. 실패한 입력·복원은 기존 프로젝트에 부분 자료를 등록하지 않는다. 작업 취소는 Worker 종료와 JobGate의 jobId/scopeId 차단을 함께 사용한다.
- 화면 텍스트는 React 텍스트 경로, 차트는 HTML 툴팁을 사용하지 않는 경로, 보고서는 이스케이프·스크립트 없는 CSP와 인쇄 격리를 유지한다. 이번 입력·출력 회귀 검사 통과를 모든 화면의 XSS 부재 증명으로 확대하지 않는다.
- 새 pako 2.1.0·saxes 6.0.0·xmlchars 2.2.0은 번들·오프라인 캐시·라이선스 파일에 포함한다. 런타임 CDN이나 사용자 자료 업로드를 추가하지 않았다. 압축 해제 바이트 제한은 XML 문자열·자료 객체·화면 사본까지 포함한 JavaScript 전체 힙의 상한이 아니다.
- GitHub Pages의 같은 출처 아래 다른 저장소 경로는 보안 경계가 아니다. 경로별 IndexedDB·캐시 이름 분리는 충돌 방지이며, 같은 출처의 다른 페이지에 대한 접근 격리를 제공하지 않는다.
- Excel 16.0.10417.20228의 구형 CSV 가져오기에서 셀 내부 단독 LF가 추가 행으로 나뉘는 호환성 제한은 CSV 수식 방어와 별개다. 정상 여러 줄 문자열의 정확한 전달은 XLSX와 대상 표 도구의 실제 재열기 결과로 판단한다. CSV는 자료형·null/빈 문자열을 완전 복원하는 형식도 아니다.
- 모든 Excel/LibreOffice 버전, 브라우저 엔진, ZIP 생산 도구, 저사양 PC, 한도 안의 모든 조합은 확인하지 않았다. Pages는 이번 소스로 재배포하지 않았으므로 로컬 보강이 공개 앱에 적용됐다고 보고하지 않는다.
